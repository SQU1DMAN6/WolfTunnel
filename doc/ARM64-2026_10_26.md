# ARM64 Linux support and validation

26 October 2026. Implemented against the managed-renderer WolfTunnel v0.5 codebase.

## Result

The node now selects a pinned native ARM64 renderer instead of rejecting ARM64
with `RENDERER_PLATFORM_UNSUPPORTED`. The node and SDL client compile for Linux
ARM64. ARM64 binaries were executed under QEMU on this amd64 development machine;
all executed checks passed. No remote Wolf Node or remote SSH server was used.

The ARM64 node downloaded its renderer on first launch, became ready on loopback
port 13300, issued an invitation and authenticated an ARM64 client. Saved
credentials and a restart using saved settings also passed. First launch,
including the fresh download, took **24.561 seconds under emulation**.

The ARM64 desktop client separately connected to an actual sandboxed amd64 node,
displayed a public HTTPS page with HTTP 200, decoded two pixel frames and received
four mouse/physical-key input acknowledgements. A screenshot was captured and
visually inspected. This validates the ARM64 client against the real protocol and
renderer, not a mocked pixel stream. The same frontend suite and public pixel/input
flow also passed with Ubuntu 24.04's ARM64 libc and an SDL build linked against
that distribution's libraries.

**Remaining hardware validation:** the complete ARM64 Chromium session inside
bubblewrap, nested Chromium namespace/seccomp sandbox and systemd cgroups has
not been run on an ARM64 Ubuntu kernel. QEMU user-mode checks do not establish
that kernel/sandbox behavior or real ARM desktop display/GPU performance. The
ARM64 browser executable itself successfully ran `--version` with Ubuntu 24.04
ARM64 runtime libraries under QEMU. The full sandboxed rendering/input/isolation
regression suite passed on the amd64 host.

## Cause and implementation

The installer embedded only a `linux-amd64` manifest and compared it with
`runtime.GOOS + "-" + runtime.GOARCH`, so every ARM64 first launch failed before
starting a browser. The Makefile also hard-coded the amd64 engine path and
deployment filename.

A second issue appeared during the cross-build: native diagnostic capture used
`syscall.Dup2`, which is unavailable on ARM64 Linux. This prevented a clean ARM64
build independently of runtime selection.

Changes:

- `internal/renderer/runtime.go` selects an embedded manifest for `linux-amd64`
  or `linux-arm64`. Normal startup selects the executing architecture. Unsupported
  targets receive an error naming the requested and supported platforms.
- `runtime-lock-linux-arm64.json` pins the official Chrome for Testing ARM64
  archive, executable and all **301 files**. The amd64 manifest is unchanged.
- Runtime cache paths include the CPU architecture. Hash validation, bounded
  HTTPS downloads/extraction, the install lock, complete asset verification,
  symlink/path rejection and atomic publication apply equally to both targets.
  An ARM64 archive supplied for amd64 is rejected.
- `EnsureFor` and `-prepare-renderer -renderer-platform linux-arm64` permit
  explicit cross-platform release provisioning. A running node cannot use this
  option to choose a renderer for another CPU.
- The Makefile respects `GOOS`/`GOARCH`, selects the corresponding engine path,
  runs the provisioning tool on the build host and packages only the target
  runtime. ARM64 packaging no longer tries to execute ARM64 code on amd64.
- Diagnostic descriptor redirection uses Linux `dup3(..., 0)` on both targets.
  Terminal forwarding, bounded capture and safe log categorization are retained.
  The subprocess regression test can re-exec through `WOLF_TEST_EXECUTOR`, avoiding
  any system-wide binfmt changes for emulated tests.
- `SETUP.md`, `frontend/README.md`, the architecture and threat-model documents
  describe native ARM64 builds, target SDL libraries, Ubuntu prerequisites and
  SSH/display requirements. USAGE.md remains short and unchanged.

The renderer remains application-private; installing system Chromium is not
required. Node builds remain pure Go with `make node`. The desktop client uses
cgo and must link SDL3 3.4.18 and SDL3_ttf 3.2.2 for its target architecture.

## Build and deployment

On the ARM64 Ubuntu host, install the prerequisites in [SETUP.md](../SETUP.md),
then use the same commands as before:

```sh
make clean
make node
./build/wolfnode
```

The installer selects ARM64 automatically. Existing node state, certificate pins
and client authorizations are preserved; changing the renderer architecture does
not require deleting state or issuing new credentials to existing clients.
An earlier failed first launch can simply be retried with the updated executable.

For an offline ARM64 deployment bundle, either build on ARM64 with
`make node-package` or cross-package from amd64:

```sh
make node-package GOOS=linux GOARCH=arm64
```

Deploy `build/wolfnode-linux-arm64.tar.gz`, keeping its `renderer/` directory beside
the node. The package was inspected to confirm an AArch64 node and AArch64 engine
and to exclude the amd64 renderer. Cross-packaging replaces `build/wolfnode` with
the target executable; run `make node` to restore the build machine's native node.

Build the client on an ARM64 desktop with native ARM64 SDL development libraries,
then `make build`. An amd64 SDL library cannot satisfy ARM64 cgo linking. Native
Ubuntu source-build instructions for the pinned SDL versions are in
[frontend/README.md](../frontend/README.md). A plain SSH terminal is sufficient
for the headless node; interactive use of the client requires a graphical session.

`results.json` summarizes the machine-readable outcomes. `cleanup.json` confirms
zero listeners on port 13300, zero active browser scopes and no temporary test
state left behind. Temporary toolchains, QEMU, Ubuntu library trees and downloaded
test archives were removed. Both packaged runtimes and test logs/screenshots were
retained under `build/`; the regular `build/wolfnode` and `build/wolfclient` were
restored to native amd64 builds for this machine. No existing user state was used
or removed.

ARM64 internal test reproduction, with a locally available QEMU executable:

```sh
GOOS=linux GOARCH=arm64 CGO_ENABLED=0 \
WOLF_TEST_EXECUTOR=/path/to/qemu-aarch64-static \
go test -exec /path/to/qemu-aarch64-static ./internal/... -count=1 -timeout 180s
```

The real archive check is opt-in:

```sh
WOLF_RENDERER_ARCHIVE_ARM64=/path/to/chrome-linux-arm64.zip \
go test ./internal/renderer -run TestARM64RuntimeArchive -count=1 -timeout 90s
```

The skipped ARM64 browser integration checks were not counted as successful ARM64
rendering tests. They require a native ARM64 kernel, the managed engine and working
isolation. On amd64, the corresponding integration checks ran against the real
managed engine, including forms/Unicode/keyboard/mouse input, screenshots,
service-worker/HTTPS egress restrictions, private-address blocking, crash recovery,
resource bounds, separate control/pixel channels and slow consumers.

The emulated client was built with a temporary ARM64 cross toolchain and software
SDL backend. SDL was also rebuilt against Ubuntu 24.04 headers/libraries and the
client/frontend tests rerun with that distribution's libc. This caught the need
to avoid newer libc symbol versions in SDL binaries built using a newer sysroot.
The Ubuntu-compatible SDL build and font-shaping library required at most
GLIBC_2.38; Ubuntu 24.04's libc is 2.39. The client executable required at most
GLIBC_2.34. Its test binaries are validation artifacts, not portable client
distribution packages. Build locally or against the intended distribution's
sysroot when shipping clients. Emulation timings are not ARM performance claims.

The trusted-node model is unchanged. Client contents/input/pixels use pinned TLS;
sites see the node's egress network identity. Timing, traffic volume, website logins
and fingerprinting still limit anonymity. No architecture-specific bypass of
pin verification, egress controls, seccomp, namespaces or resource limits exists.

Ubuntu may restrict unprivileged/nested user namespaces through
[AppArmor](https://documentation.ubuntu.com/security/security-features/privilege-restriction/apparmor/#apparmor-unprivileged-user-namespace-restrictions).
The host administrator must permit the application's required namespace operations
in appropriate profiles. Bubblewrap, common browser libraries, an ordinary user
account, a functioning systemd user manager/cgroup v2 and adequate resources remain
requirements. WolfTunnel does not disable AppArmor, run the browser as root or
add `--no-sandbox` to bypass a host restriction.

Engine maintenance, native ARM64 Ubuntu sandbox verification, hardware display
testing and distribution-specific client packaging remain release considerations.
